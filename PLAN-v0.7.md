# fove v0.7 — daily driver

The goal for this round is narrow: **fove replaces the editor for a full day of
work on `core`, without falling back to VS Code.**

v0.5 made it a real app. What stops it being a daily driver is that you cannot
create a file, cannot step through code, cannot see the page you are changing,
and have to hand-wire a worktree before it runs.

Grounded against the actual `core` setup rather than assumed — findings marked
**[verified]** were checked on this machine.

**Decided, not to be re-litigated:**

1. **Build order is friction-first:** editor basics → worktree recipes →
   browser → debugger. The first two are small and remove daily annoyance
   immediately; the debugger goes last because it is the one item that can
   swallow a release, and it is safest to start once everything around it is
   stable.
2. **The debugger is Python-only.** `core` is Flask, so `debugpy` covers the
   code actually stepped through. Node is deferred: it needs either a CDP
   bridge or `vscode-js-debug` as an adapter, roughly doubling the transport
   work for the language debugged less here.

---

## 0. Already works — do not build

**Pre-commit hooks.** You asked whether these are "a function of the terminal
and already work". They are, and they do:

- `core/.git/hooks/pre-commit` is generated by `pre-commit` (black, on
  `pre-commit` and `pre-push`). **[verified]**
- A worktree's `.git` is a *file* pointing at
  `core/.git/worktrees/<name>`, so every worktree shares the main repo's
  hooks. **[verified]** No per-worktree install needed.
- fove's commit runs plain `git commit`, so hooks fire, and v0.5 already
  surfaces a failing hook's output verbatim (there is a test for exactly
  this).

Nothing to do. The only possible addition is a **"commit without hooks"**
affordance — `--no-verify` is already implemented in `gitWrite.ts` but has no
button, deliberately: it should be awkward to reach.

## 1. Editor: the basics that make it an editor

Today the file tree can only *open* files. Missing, in the order they hurt:

| Action | Notes |
|---|---|
| **New file / new folder** | Inline in the tree, at the selected directory. |
| **Rename** | `fs.rename`. Must move the open Monaco model with it, or the tab silently points at a path that no longer exists. |
| **Delete** | To the system trash (`shell.trashItem`), never `unlink` — this is the one action a user cannot undo, and the OS already has an undo for it. |
| **Duplicate** | `foo.ts` → `foo copy.ts`, resolving collisions. |
| **Copy path / copy relative path** | The single most-used command in VS Code's tree. Relative to the workspace root. |
| **Reveal in Finder** | Already exists as an IPC channel; just not in the tree. |
| **Context menu** | Right-click. Everything above hangs off it. |
| **Unsaved indicator** | A dot on a dirty tab, and a prompt before closing it. |
few more things: cmd click to go to the defination, rendering the correct linter, codebase search :) lets add these too

**Two things that will bite:**

- **Renaming an open file.** Monaco keys models by path (`modelsRef`), so a
  rename has to re-key the map and update the tab, or the editor keeps writing
  to the old path. Same for delete.
- **The file watcher.** There isn't one. A file changed by an agent — the
  common case here — does not refresh the tree, and the editor's mtime guard
  will reject the save with a conflict. `fs.watch` on the open directory,
  debounced, is enough.

Small, mechanical, and the highest ratio of "daily annoyance removed" per hour
on this list. **Do this first.**

## 2. Debugger

The largest item. Scope it or it swallows the release.

**Decided: Python only in v0.7.** `core` is Flask — that is the code you
actually debug. **[verified: `debugpy` is not installed; it is a `pip install`
away.]** Node is deferred to a later round for the reason given above.

**Protocol.** Python speaks DAP (Debug Adapter Protocol), the same wire format
VS Code uses: `debugpy`, launched as
`python -m debugpy --listen <port> --wait-for-client`.

(Node, when it comes, speaks CDP through its built-in inspector
(`node --inspect-brk`) and needs either a bridge or `vscode-js-debug` as an
adapter — which is exactly why it is not in this round.)

DAP is JSON-RPC over a length-prefixed stream — the same shape as the IDE
protocol already implemented in `ide.ts`, so the transport work is understood.

**What ships:**
- Breakpoints in the Monaco gutter (Monaco has a decorations API for this).
- Step over / into / out / continue, and a stack view.
- Variables and scopes for the selected frame.
- A watch/REPL box evaluating in the paused frame.
- Launch configs read from `.vscode/launch.json` when present — you already
  have those, and inventing a fove-specific format would be worse.

**Deliberately not in scope:** conditional breakpoints, hot reload,
multi-target sessions, remote attach. Add them once the basics are trusted.

**The risk to name:** a debugger is a *stateful* protocol against a live
process. Unlike everything in fove so far, "read it again" is not a recovery
strategy. Build the adapter client as a pure module with a fake adapter in
tests, exactly as the layout engine and commit graph were done.

## 3. Browser: inline testing

You said "just a chromium integration should be fine", and that is the right
call — Electron *is* Chromium, so this needs no dependency.

**Use `WebContentsView`.** `BrowserView` is deprecated in this Electron
version. **[verified in `electron.d.ts`]**

A browser pane holds: a URL bar, back/forward/reload, and the page. Beyond
that, the parts that make it *inline testing* rather than a browser:

- **Console + network capture**, so a failing request is visible next to the
  code rather than in a separate window.
- **Auto-reload on save** — the loop that makes a browser pane worth having at
  all when the editor is beside it.
- **"Open what I'm working on"** — detect a dev server (Flask's 5000, Vite's
  5173) and offer it rather than making you type a URL.
- **Element → source**, eventually. Deep; defer.

**Give Claude access to it.** This is the part that is genuinely fove-shaped
rather than a browser bolted on: the IDE server (`ide.ts`) can expose a tool
that returns the current console errors and failed requests, so "why is this
page broken" is answerable without copy-paste. Nothing else in this list
compounds with the AI layer the way this does.

**Security:** the pane loads arbitrary pages. `contextIsolation` on,
`nodeIntegration` off, and a separate session partition from the app itself.
Non-negotiable — this is the one feature that puts untrusted code in the
process.

## 4. Workspace setup: make a worktree usable in one click

This is the item with the clearest evidence behind it, and it is currently
*inconsistent on your own machine* — which is the argument for automating it:

- `conductor/workspaces/core/cape-town/.env` → **symlink** to
  `core/.env` **[verified]**
- `.warp/worktrees/core/AGENT/.env` → **a copied regular file** **[verified]**

The copy silently goes stale the moment `core/.env` changes. You have 5+
worktrees across three tools (`conductor`, `.warp`, and the main checkout), and
each one is hand-wired.

**What to build — a per-project setup recipe**, stored in fove (not in the
repo, since this is machine-local):

```jsonc
// ~/.config/fove/workspaces/<repo>.json
{
  "link": [".env", ".env.local"],       // symlink from the primary checkout
  "run":  ["uv sync"],                  // after creating a worktree
  "open": ["flask/core"]                // pane layout to restore
}
```

Then: **"New worktree"** in the git pane creates the branch, applies the
recipe, and opens a tab on it. One click instead of a manual checklist.

Rules worth stating:
- **Symlink, never copy.** The copied `.env` is already a bug waiting to
  happen; fove should not create more of them.
- **Never overwrite an existing file** without saying so — a `.env` with local
  edits in it is exactly the file you cannot afford to clobber.
- The recipe lives outside the repo, so it cannot leak machine paths into a
  commit.

## 5. Ideas worth considering

Not asked for; offered because they follow from what is already built.

**0. pop out a pane so that I can work in another screen, that would make my life really easy too.
**a. Worktree switcher with live status.** You have 5+ worktrees. A palette
listing each with its branch, dirty-file count, and whether an agent is
currently running in it — jump straight to one. fove already reads all three
facts.

**b. "What changed while I was away."** After an agent's turn, a single diff of
everything it touched across all files, reviewable in one pass rather than
file-by-file. The diff view and the agent tree both exist; this joins them.

**c. Test runner pane.** `pytest` with failures as a list, click to jump to the
line. Pairs directly with the debugger: a failing test is the most common
reason to start one.

**d. Command palette (⌘P / ⌘⇧P).** Files, actions, worktrees, sessions. Once
the surface area is this large, a palette is how you stop hunting for buttons.

**e. Agent cost per turn.** The rail now tracks the pane's own session
correctly; showing tokens *per turn* rather than cumulative would make an
expensive prompt obvious immediately.

**f. Those 32 auto-installed agents.** Deferred to **0.9**, together with the
equivalent question for skills: does a definition actually load into the system
prompt every session, and does the thing still work once toggled off? None of
the 32 has run in 157 sessions, so if their descriptions are loaded, that is
context paid for and not chosen -- but "existence and working checks" for both
agents and skills belong in one pass rather than piecemeal.

## 6. Editor intelligence

Three requests, and they differ sharply in cost. Grounded in what is actually
installed **[verified]**:

- Monaco ships a TypeScript/JavaScript language service, and **nothing for
  Python** — only syntax highlighting.
- No standalone Python language server is installed (`pyright`,
  `pyright-langserver`: absent). **Pylance is present but is licensed for use
  in Microsoft editors only** and cannot be bundled here.
- `ruff` **is** installed, and `rg` 15.1.0 is available.

**a. Codebase search — cheap, do it first.** `rg --json` gives matches with
line and column already parsed. A results pane with click-to-open reuses the
`openInPane` path that already exists. No new dependency, no protocol.

**b. Linting — cheap for Python, free for TS.**
- Python: run `ruff check --output-format=json` on save and render the
  diagnostics as Monaco markers. Ruff is fast enough to run per save and is
  already on this machine.
- TS/JS: Monaco's bundled service already does this; it only needs the
  compiler options wired up so it stops complaining about module resolution.

**c. Cmd-click to definition — the expensive one.** This is the item to be
honest about:
- For TS/JS, Monaco's own service provides it once the file is in its model
  graph. Mostly configuration.
- For Python it needs a real language server, and there is no ready one on this
  machine. The options are to require `pip install pyright` (Node-based, works
  as a plain LSP), or to build a heuristic "jump to symbol" from `rg` — which
  is not the same thing and will be wrong on shadowed names.

**Decided:** search, Python linting and TS/JS Cmd-click all ship in v0.7 —
none of them needs a language server. **Python go-to-definition comes after
the debugger**, deliberately: an LSP client is a stateful protocol with
document synchronisation, the same class of work as DAP, so the debugger
should teach that shape first.

## 7. Pop a pane into its own window

The clearest win per hour on this list, and it needs no new protocol: a pane
becomes a separate `BrowserWindow` on a second screen, keeping its PTY alive.

The whole design constraint is **do not remount the pane**. A remount tears
down the PTY and kills a running `claude` session, which is exactly what makes
this feature worth having in the first place. Two workable approaches:

1. **A second window rendering the same pane id.** The PTY lives in the main
   process and is addressed by pane id, so a new window can attach to the same
   session, replay the scrollback the service already retains, and receive the
   same `pty:data` events. The layout tree marks the pane as "popped" and
   leaves a placeholder behind.
2. Native view reparenting — rejected. Fragile across platforms for no gain
   over (1).

Scope: pop out, pop back in, and remember the popped state across a restart.
Cross-window drag is not in scope.

## 8. Worktree switcher

You have 5+ worktrees across three tools. fove already reads every fact
needed: `git worktree list`, the dirty count from `status`, and whether a
Claude session is live in that directory from `sessionLink.ts`.

A palette (⌘⇧O) listing each worktree with its branch, dirty-file count and
agent status, opening the chosen one as a tab. The pieces exist; this is
assembly, not new machinery.

Worth pairing with a general **command palette** (§5d) rather than building a
one-off list widget — the worktree switcher is the first useful thing to put
in it.

  passed its unit tests and appeared only when driving the real thing.
